# ⚠️ 这个目录里的日志是**过期产物**，不要拿它下结论

这 6 份 `headless-sim-*.log` 记录的是**一次失败的模拟运行**（S6 失败、平均推进 4.2 房、平均击杀 13）。

**但它们不等于当前代码的行为。** 用当前代码复跑同样参数，结果是 **6/6 全绿、平均 27 杀、真·卡死 0**。

## 怎么确认是日志过期、而不是代码退化了

`tools/sim.gd` 的种子是 `seed64 = seed0 + i * 7919`，`seed0` 默认 **1000**。
用当前代码复跑，打印的是：

```
1000 / 8919 / 16838 / 24757 / 32676 / 40595
```

而这 6 份日志里打印的是：

```
3000 / 10919 / 18838 / 26757 / 34676 / 42595
```

**第一局差 2000，后五局完全相同** —— 说明生成这些日志时 `seed0` 被设成了 3000，而 `sim.gd` 的 mtime 没有如实反映这次改动。

同一局对比更直白：日志里的 `seed 26757` 是「帧 24000 上限用尽」（卡住），
当前代码复跑同一局是「房 9/11、帧 33405、`floor_clear`」（通关）—— **卡住和通关整个翻过来了**。

## 所以

- **要看当前行为，请自己跑**：`godot --headless --path . --script tools/sim.gd -- --runs=6 --frames=24000`
- 完整的复现说明与证据在仓库根 README 的 **§4.3**
- 保留这些日志的唯一理由是**留痕**：它记录了一次真实的踩坑——**日志头部只打印 `runs=` / `max_frames=`，不打印种子，导致事后无法溯源、无从复现**。这是这套工具链缺的东西，不是可以忽略的小事。

> 附带教训：任何"证据文件"如果缺少能唯一确定运行条件的字段（这里就是种子），它就在几个月后变成陷阱。
